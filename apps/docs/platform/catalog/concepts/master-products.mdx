In this document, you'll learn how products are modelled: every product belongs
to the store that created it, and the store sells it directly through the
product's own variants.

## Product

A product is Medusa's native `Product` data model (table `product`, id prefix
`prod`). It carries the usual commerce fields such as `title`, `handle`,
`description`, `status`, variants, options, and images. When a store creates a
product, the product is linked to that store through the `product_seller` link,
and only that store can see, edit, or delete it.

```ts
const { result } = await createProductsWorkflow(container).run({
  input: {
    products: [
      {
        title: "Aeron Chair",
        status: "proposed",
        seller_ids: ["sel_123"],
      },
    ],
    created_by: "sel_123",
  },
})
```

<Note>
  There is no separate listing entity between a product and a store. The
  store's SKU, price, and stock live on the product's own variants (Medusa
  variant prices and inventory items), and the product's shipping profile
  belongs to the same store. A cart line item points at a variant, and the
  line item's store is the store linked to the variant's product.
</Note>

## Ownership and audit

The `product_seller` link is the ownership record. Vendor routes only return
products linked to the authenticated store (or created by it), and any other
product id answers `404`. Every submission and edit is also recorded as an
immutable audit entry in the product-change pipeline (for example a
`PRODUCT_ADD` action) so you know who changed what.

<Tip>
  Attribution is recorded automatically by `createProductsWorkflow` through its
  `created_by` input. You don't manage it by hand. See the
  [status lifecycle](/platform/catalog/concepts/status-lifecycle) for how a
  submission becomes a published product.
</Tip>
